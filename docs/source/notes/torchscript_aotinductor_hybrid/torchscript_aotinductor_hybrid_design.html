Technical design proposal

Hybrid TorchScript orchestration with AOTInductor regions

Preserve TorchScript's data-dependent control flow and portable execution model while delegating explicitly annotated compute regions to torch.export and AOTInductor.

Status: Proposed Primary decision: JIT backend delegation Initial scope: Inference Audience: Compiler and runtime engineers Updated: July 14, 2026

Executive summary

The system compiles the outer model with TorchScript and replaces marked submodules with typed, opaque backend modules. Each marked body is independently captured by torch.export, compiled by AOTInductor, and invoked through the existing TorchScript backend interface.

Recommendation Use a registered PyTorchBackendInterface implementation as the runtime boundary. Compile annotated regions before recursive scripting, generate schema-only TorchScript stubs, lower those stubs to the AOTI backend, and then script the outer model.

This keeps control flow such as if, loops, recursion supported by TorchScript, and method dispatch in the outer graph. AOTInductor sees only coarse compute regions and can perform fusion, scheduling, memory planning, and target-specific kernel generation within each region.

Goals and non-goals

Preserve outer control flow

Tensor-dependent TorchScript branches and loops may select or repeatedly invoke compiled regions.

Use the export stack locally

Annotated regions receive export's normalized graph and AOTInductor's target-specific optimizations.

Retain typed boundaries

Outer TorchScript sees the original method signature rather than an untyped global callback.

Support C++ execution

The final artifact loads without Python and reconstructs its AOTI runners during deserialization.

No cross-boundary fusion

TorchScript and Inductor optimize their own sides of the boundary; the boundary remains opaque.

No training in version one

Parameters are frozen into AOTI artifacts and autograd does not cross the delegated call.

No automatic region discovery

Programmers choose regions explicitly. Automatic partitioning can be evaluated after the ABI stabilizes.

No implicit recompilation

A deployed region either accepts its input contract or returns a precise runtime error.

Proposed user experience

The annotation records configuration only. Compilation remains explicit because export requires representative inputs and a shape contract.

from torch.export import Dim
from torch.hybrid import aoti_region, compile

class FastBlock(torch.nn.Module):
    @aoti_region(
        dynamic_shapes={
            "x": {0: Dim("batch", min=1, max=1024)},
        },
        options={"max_autotune": True},
    )
    def forward(self, x: torch.Tensor) -> torch.Tensor:
        return self.proj(torch.relu(x))

class Model(torch.nn.Module):
    def __init__(self) -> None:
        super().__init__()
        self.fast = FastBlock()

    def forward(self, x: torch.Tensor) -> torch.Tensor:
        if x.sum() > 0:
            return self.fast(x)
        return x - 1

model = Model().eval()
compiled = compile(
    model,
    calibration_inputs=[
        ((torch.randn(8, 10, device="cuda"),), {}),
    ],
    target="cuda",
)
compiled.save("model.pt")

Calibration hooks record concrete region inputs. If a region is not reached, compilation fails with its qualified name and asks for region_inputs={...}. Silent omission would produce an artifact whose behavior depends on calibration coverage.

System architecture

Runtime ownership and call boundary

Python frontend

The frontend owns decorators, discovery, calibration, export, AOTInductor invocation, schema stub generation, temporary module substitution, correctness checks, and packaging. Annotation metadata must remain inert during normal eager execution.

TorchScript backend

Register AOTIRegionBackend : PyTorchBackendInterface. The existing backend contract provides compile(processed, method_compile_spec) and execute(handle, List[Any]). Generated wrapper methods preserve the original schema while adapting calls to that boxed interface.

AOTI runtime

Each backend instance owns one or more AOTIModelPackageLoader objects. Its compile method materializes precompiled package bytes and creates runners; it does not invoke Inductor during model load.

Why substitute before scripting? Recursive scripting would otherwise compile the annotated region body. Replacing it with a schema-only lowered stub first means a region needs to satisfy the export contract, not both the export and TorchScript language subsets.

Compile-time flow

Discover regions

Walk the eager module hierarchy, normalize class and method annotations, assign stable qualified region IDs, and reject nested or conflicting annotations.

Validate state

Require evaluation mode, identify parameters and buffers owned by each region, and reject shared state, hooks, unsupported mutation, or direct parent access to region internals.

Capture examples

Run top-level calibration cases with temporary hooks and record region arguments, keyword binding, tensor metadata, autocast state, and device.

Export each region

Call torch.export.export(..., strict=True), apply the annotation's dynamic shape contract, and inspect the graph signature for mutation and aliasing.

Compile and verify

Run aoti_compile_and_package into an in-memory package, load it, and compare eager and AOTI outputs on all captured examples.

Build typed stubs

Generate a body-less ScriptModule from the Python annotations or explicit schema, attach the package payload and manifest, and lower it through the AOTI JIT backend.

Script the outer model

Temporarily substitute lowered regions into the eager hierarchy, call torch.jit.script, and restore the user's model in a finally block.

Validate end to end

Compare the final hybrid ScriptModule with eager execution across calibration cases, then attach provenance and build metadata.

Runtime behavior

Outer execution remains ordinary TorchScript. A branch or loop decides whether and how often the lowered submodule is called.

%pred = aten::gt(%sum, %zero)
%result = prim::If(%pred)
  block0:
    %fast = prim::GetAttr[name="fast"](%self)
    %y = prim::CallMethod[name="forward"](%fast, %x)
    -> (%y)
  block1:
    %y = aten::sub(%x, %one, %alpha)
    -> (%y)
TorchScript path

Evaluates dynamic control flow and invokes ordinary scripted operators and modules.

AOTI region path

Backend method behavior

  1. Resolve the method handle to a loaded package runner.
  2. Flatten supported TorchScript values according to the stored ABI manifest.
  3. Validate device, dtype, rank, strides, static dimensions, and symbolic range constraints.
  4. Invoke the runner on the current device stream without an implicit synchronization.
  5. Rebuild the declared return structure and return it through List[Any].

The runtime must use a runner pool or the AOTI model container's concurrency support rather than placing a global lock around every region. Runner count is a compile option and must be included in the manifest.

Serialization and artifact layout

The default artifact remains a TorchScript archive. Every lowered module stores its AOTI package as a CPU uint8 tensor in serialized backend state. Live runner handles are excluded and reconstructed during __setstate__. 

model.pt
  code/                         TorchScript methods and classes
  data/                         TorchScript tensors and constants
  hybrid_manifest.json          Global region index and compatibility data
  aoti_payloads/                Logical payloads stored through backend state
    encoder.fast/<hash>.pt2     AOTInductor package bytes
    decoder.mlp/<hash>.pt2

At load, the backend hashes each payload, writes it atomically into a content-addressed cache, validates compatibility metadata, and constructs AOTIModelPackageLoader. The cache prevents repeated extraction when many model instances share an artifact.

Control flow

TorchScript may place arbitrary supported control flow around the region. Inside the exported region, ordinary Python data-dependent branches remain subject to export rules and should use structured operators such as torch.cond or torch.while_loop when dynamic semantics must be preserved.

State and device movement

Region parameters and buffers are frozen into the AOTI package. Calling .to(), loading a new state dict, or switching training mode after hybrid compilation is unsupported. The compiler should remove delegated parameters from the visible outer ScriptModule state and preserve an FQN-to-constant mapping for diagnostics.

Boundary granularity

Every call pays method dispatch, boxing, validation, and AOTI runner overhead. There is no fusion across the boundary. Documentation and tooling should recommend whole blocks such as attention, convolution stacks, or MLPs rather than individual pointwise operators.

Free-function support

Version one: bind as a submodule

@aoti_region(dynamic_shapes={"x": {0: batch}})
def fast_fn(x: torch.Tensor) -> torch.Tensor:
    return torch.relu(x @ weight)

class Model(torch.nn.Module):
    def __init__(self) -> None:
        super().__init__()
        self.fast_fn = torch.hybrid.bind(fast_fn)

    def forward(self, x: torch.Tensor) -> torch.Tensor:
        return self.fast_fn(x)

bind creates a synthetic nn.Module whose forward has the function's annotated signature. This reuses the same ownership, serialization, and lowering path as an ordinary marked submodule.

Version two: direct calls

Direct fast_fn(x) calls require a whole-program TorchScript transformation. The compiler must find annotated prim::CallFunction nodes, lift a lowered module into the nearest owning ScriptModule, and rewrite calls to prim::CallMethod. Calls inside helper functions require inlining or threading a hidden region context through the call graph.

Avoid a process-global runner registry A generic operator keyed only by a string is simpler, but creates model lifetime, namespace collision, unload, concurrency, and multi-tenant isolation problems. Region runners should remain owned by serialized module state.

Validation, errors, and fallback

Compile-time validation

  • Every annotated region must be reached by calibration or receive explicit region examples.
  • Python annotations or an explicit schema must fully define the TorchScript boundary.
  • All observed calls must fit one export shape contract or compilation fails with the conflicting examples.
  • Export graph signatures must contain no unsupported mutations or aliases.
  • Eager, exported, AOTI, and final hybrid outputs must agree on supplied validation cases.

Runtime errors

Errors should include the region FQN, artifact hash, expected contract, actual tensor metadata, and the stage that failed. For example:

HybridRegionError: encoder.fast rejected input 0
  expected: float16 cuda rank=3 shape=[1..1024, 128, 64]
  actual:   float16 cuda rank=3 shape=[2048, 128, 64]
  artifact: aoti:8d9f...c21
  action: widen the annotated Dim range and rebuild the artifact

Fallback policy

The default is error. An optional fallback="script" mode may retain a scripted copy of the original region and dispatch to it when a cheap preflight guard fails. This is only available when the original body is also TorchScript-compatible and immutable; it increases artifact size and must not catch execution failures after kernels have launched.

The implementation should minimize new frontend and IR surface area, build on the existing backend extension point, and isolate the region compiler so a future orchestrator such as structured export control flow or NativeRT can reuse the AOTI packaging and ABI components.

Implementation plan

Phase 1: Backend proof

Register the AOTI JIT backend, embed one package payload, load it after TorchScript save/load, and execute a flat tensor ABI on CPU and CUDA.

Phase 2: Annotated submodules

Add decorators, calibration capture, strict export, typed stubs, substitution before scripting, validation, and qualified diagnostics.

Phase 3: Production artifact

Add content-addressed extraction, compatibility manifests, provenance, runner pooling, package integrity checks, and C++ loading tests.

Phase 4: ABI expansion

Support nested tensor containers, optional tensors, multiple methods, target variants, and an opt-in scripted fallback.

Phase 5: Direct functions

Implement function lifting and TorchScript callsite rewriting only after module ownership and serialization semantics are stable.

Phase 6: Migration path

Evaluate reusing the region ABI from structured export control flow or NativeRT to reduce long-term dependency on TorchScript internals.

Test strategy

  • Control flow: tensor-dependent if, loops, nested branches, and multiple invocations of one region.
  • Correctness: eager versus export versus AOTI versus final hybrid results over static and dynamic shapes.
  • Serialization: Python and C++ save/load in clean processes with no compile-time filesystem paths available.
  • Contracts: wrong dtype, device, rank, stride, static dimension, and dynamic range produce stable errors.
  • State: shared parameters, hooks, mutation, aliases, training mode, and post-compile state updates are rejected.
  • Concurrency: multiple threads, multiple model instances, CUDA streams, runner pools, and artifact cache races.
  • Compatibility: missing backend registration, incompatible AOTI ABI, target mismatch, and corrupt package payload.
  • Performance: quantify boundary overhead and publish minimum recommended region granularity.
  • Diagnostics: region FQNs and source provenance survive all compilation and serialization stages.

CI should include at least one C++ integration test that loads the final TorchScript artifact, takes both sides of a scripted branch, and executes an AOTI region without importing Python.

Open questions

  1. Should package bytes remain embedded in TorchScript state, or should the public artifact become a higher-level archive containing both TorchScript and AOTI payloads?
  2. Should the first public ABI allow nested tensor pytrees, or begin with flat tensors and add containers after serialization is stable?
  3. What exact compatibility promise can AOTI artifacts make across PyTorch releases and target driver versions?
  4. Should runtime input checks always be enabled for hybrid regions, independent of the global AOTI runtime-check setting?
  5. Is an optional scripted fallback worth its artifact size and state duplication, or should all contract failures remain fatal?
  6. Can the AOTI package loader accept a memory-backed package directly to avoid materializing nested package bytes?
  7. What is the long-term outer control-flow runtime once TorchScript maintenance no longer justifies new integrations?
